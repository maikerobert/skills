# Portable Code Standard

By Maike Robert. MIT License.

AI tools that generate systems tend to leave two marks on the code. The first is a signature: the tool's name shows up in classes, functions, files, comments and commit messages. The second is lock-in: the tool reaches for its own authentication, database, storage or deploy by default, and the system only works while it stays inside that platform.

This standard makes generated code belong to the team that will maintain it, readable without knowing which tool wrote it, and able to run on whatever infrastructure the team chooses.

## Before you start

1. Read the project's `AGENTS.md`, `README` and configuration. If they define providers (auth, database, hosting), use them. This standard never overrides a decision the team has already recorded.
2. If the task needs a provider the project has not chosen yet, ask before choosing. Never adopt the tool's embedded service just because it is the shortest path.
3. If the user explicitly asks for a platform service, use it, isolate it as described in rule 2, and record the dependency in the README.

## The 6 rules

### 1. Neutral authorship

The code does not mention who wrote it.

- No AI or AI tool names in classes, functions, variables, constants, files, folders, packages, branches, logs or error messages. `ManusAuthProvider`, `claudeHelper.ts` and `// created by ChatGPT` are not allowed.
- No comments such as "generated by AI", "created with the help of", "Generated by". Comments explain why the code exists, never who wrote it.
- Commit messages describe the change. No AI signature and no AI `Co-authored-by` trailer, unless the repository policy asks for it.
- Names come from the business domain (`AuthProvider`, `OrderService`, `calculateCommission`), never from the tool.
- Single exception: when the system deliberately integrates an AI API (for example, a module that calls a language model), the provider name appears only inside that isolated module, like any other vendor.

### 2. Platform independence

The system runs outside the tool that generated it.

- Authentication, database, file storage, email, payments, queues, analytics and hosting use the provider defined by the project. The AI tool's embedded service is never the default.
- Every external service sits behind an interface owned by the project (`AuthProvider`, `StorageService`, `EmailSender`). Switching vendors changes one adapter, not the whole system.
- The database schema lives in the repository as versioned migrations. A table created only in a platform dashboard does not exist for the project.
- Configuration comes from environment variables, with a `.env.example` listing every variable with placeholders instead of values.
- The README explains how to install, configure and run the project locally without the platform. Deploys use a standard format (Dockerfile, documented build command or versioned infrastructure file).
- Dependencies are declared in the project manifest (`package.json`, `requirements.txt`, `pyproject.toml` and so on), with a lock file when the ecosystem has one. Nothing is installed "on the side" inside the tool's environment.

### 3. Secrets stay out of the code

- No API keys, tokens, passwords, connection strings or certificates in code, comments, tests or examples.
- `.env` and credential files are in `.gitignore`. Only `.env.example` is versioned.
- If you find a secret in the code or in the history, stop, tell the user and recommend revoking and rotating it. Removing it from the code does not help once the key has been committed.

### 4. English in the code

- Variables, functions, classes, files, folders, branches, database tables and columns, API routes, events and every other identifier are in English.
- Code comments and commit messages are in English too.
- Text the end user reads (interface copy, emails, error messages shown on screen) follows the product's language and lives in copy or translation files, never hardcoded inside identifiers.

### 5. Clean repository

- No configuration, cache or draft files from the AI tool in the repository, unless the project needs them to run.
- No dead code, temporary files, debugging output or TODOs without context.
- Each commit does one thing and says what it did.

### 6. Automated checks

Written rules can be forgotten; automated checks cannot. Every repository that follows this standard installs the check below and runs it before each commit.

## Automated check (free)

The `scripts/` folder ships a ready-made check in Bash, with no dependency beyond Git.

- `scripts/check-portability.sh` looks for AI tool names in code and comments, authorship phrases ("Generated by", "gerado por IA"), common secret patterns (AWS, Google, GitHub, OpenAI and Slack keys, private keys) and versioned `.env` files. With `--all` it checks the whole repository. With `--message <file>` it checks a commit message.
- `scripts/install-hooks.sh` installs two local Git hooks: `pre-commit` (checks the staged files) and `commit-msg` (checks the message). They run on the committer's machine and cost nothing.
- `assets/portability.yml` is the optional GitHub Actions workflow to run the same check on the server. It is free on public repositories; on private ones it uses a few seconds of the free monthly quota.
- `assets/portability.example` is the configuration file. Copy it to the repository root as `.portability` to block more names (for example, a platform SDK) or to ignore paths (for example, the module that integrates an AI API on purpose).

Setting it up in a repository:

1. Copy `scripts/check-portability.sh` and `scripts/install-hooks.sh` to the project's `scripts/` folder.
2. Run `bash scripts/install-hooks.sh` once on each machine.
3. Optional: copy `assets/portability.yml` to `.github/workflows/`.
4. Optional: copy `assets/portability.example` to the root as `.portability` and adjust it.
5. Run `bash scripts/check-portability.sh --all` to see the current state of the repository.

## How to work with this standard

- **Writing code:** follow the 6 rules from the first file. Run the check before committing if it is installed.
- **Reviewing code:** list each problem with file, line, rule number and the suggested fix. Separate blockers (rules 1, 2, 3 and 4) from improvements (rule 5).
- **Moving a project out of an AI tool into its own repository:** first inventory everything that depends on the platform (auth, database, storage, variables, deploy), propose a replacement for each item, and only then change the code, one service at a time.
- **Bringing the rules to a repository:** paste the block from `references/agents-md-block.md` into the project's `AGENTS.md`. Any agent that opens the repository will follow the same rules, even without this skill installed.

## Checklist before committing

1. Any AI or tool name in code names, files, comments or the commit message?
2. Any embedded platform service used without an explicit request, or outside an adapter?
3. Is the database schema in versioned migrations in the repository?
4. Are all variables in `.env.example`, with no secret in the code?
5. Are identifiers, comments and the commit message in English?
6. Does the README let someone run the project locally without the tool that generated it?
7. Did the automated check pass?
